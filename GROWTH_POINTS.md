# Точки роста: Neon Circuit — WebGL Racing

Анализ проекта на основе полного аудита кодовой базы: 6 клиентских модулей (~1500 строк), сервер (~470 строк), 3 карты, 35 интеграционных тестов.

Текущее состояние: рабочий мультиплеерный (LAN) 3D-гоночный прототип с ретро-эстетикой, CRT-шейдером, системой лобби, таблицей лидеров, миникартой, HUD, дрифт-механикой.

---

## Категория 1: Геймплей и игровой опыт

### 1.1 Звук и музыка — полностью отсутствуют

**Описание**: В проекте нет ни одного аудио-элемента. Нет звука двигателя, скрежета о стены, визга шин при дрифте, музыки в меню или гонке, звуков обратного отсчёта.

**Обоснование**: Звук — один из главных факторов игрового «сока» (game juice). Ретро-гонки 80-х без синтвейв-саундтрека и аркадных эффектов теряют 50%+ атмосферы. Браузерный Web Audio API доступен без зависимостей.

**Что сделать**:
- Процедурный звук двигателя (oscillator, pitch ~ speed)
- Звуковые эффекты: дрифт, столкновение со стеной, финиш круга, обратный отсчёт
- Фоновая синтвейв-музыка (можно сгенерировать или взять royalty-free)
- Важно: Web Audio API требует user gesture для запуска — предусмотреть AudioContext.resume() по клику

**Сложность**: Средняя  
**Импакт**: Высокий  
**Приоритет**: 🔴 Критический

---

### 1.2 Визуальные эффекты — нет частиц, нет динамики

**Описание**: Нет визуальных эффектов, кроме CRT-шейдера и текстового «DRIFT!» в HUD. Нет дыма от шин при дрифте, искр от стен, следов торможения, анимации колёс (они статичные кубы), нет эффекта ускорения/speed lines.

**Обоснование**: Проект уже имеет стилистически сильную визуальную основу (синтвейв небо, неоновые стены, CRT), но интерактивная обратная связь минимальна. Drift-механика заявлена, но визуально почти незаметна — только наклон модели на 0.15 рад и текст в HUD.

**Что сделать**:
- Частицы дрифта (2D sprites / billboards за задними колёсами при drift > 0.3)
- Искры при столкновении со стеной (wallHit.hit === true)
- Следы торможения на дороге (декальная полоса по траектории при drift)
- Вращение колёс (сейчас колёса — неподвижные кубы, car.js:36-39)
- Speed lines / radial blur при высокой скорости

**Сложность**: Средняя  
**Импакт**: Высокий  
**Приоритет**: 🔴 Критический

### 1.3 Столкновения между игроками — отсутствуют

**Описание**: Машины игроков проезжают друг через друга. В game.js есть clampToTrack для удалённых машин (удержание в пределах трассы), но нет car-to-car коллизий.

**Обоснование**: В гоночном мультиплеере столкновения между игроками — ключевой элемент напряжения. Без них гонка превращается в параллельный тайм-аттак.

**Что сделать**:
- Простая AABB/sphere коллизия между локальным и удалёнными игроками
- Push-back обоих (для локального — физический, для удалённых — визуальный)
- Бонус: звуковой эффект столкновения, искры

**Сложность**: Средняя  
**Импакт**: Высокий  
**Приоритет**: 🟡 Важный

### 1.4 Режим одиночной игры с AI-оппонентами

**Описание**: Играть без запущенного сервера невозможно. IDEA.md заявляет «playable in under 60 seconds», но для запуска нужен npm install + npm run server. Одиночному игроку не с кем соревноваться.

**Обоснование**: Большинство пользователей хотят просто нажать Play и сразу гонять. Серверная зависимость — главный барьер входа.

**Что сделать**:
- Отдельный offline-режим, запускаемый кнопкой «SOLO RACE» на экране подключения
- 2-4 AI-машины с простой логикой: следование по spline трассы (track.curve.getPointAt(t)) с разбросом по скорости и lateralOffset
- AI не требует серверной логики, работает полностью на клиенте

**Сложность**: Средняя  
**Импакт**: Высокий  
**Приоритет**: 🟡 Важный

### 1.5 Бустеры, power-ups и трассовые элементы

**Описание**: Геймплей линейный — газ, руль, дрифт, финиш. Нет ни одного интерактивного элемента на трассе: нет бустеров (ускорение), ловушек (замедление), рамп (прыжки), нитро-механики.

**Обоснование**: MAPS.md уже определяет тип пропса `ramp` в схеме, но он не реализован. 3 круга с одинаковой механикой быстро надоедают. Power-ups добавляют вариативность и стратегию.

**Что сделать**:
- Турбо-пады на трассе (контактные зоны, увеличивающие speed на N секунд)
- Нитро-запас (копится при дрифте, активация по кнопке — моментальный буст)
- Ramp-пропс — прыжок с отрывом от земли (Y-компонента физики)

**Сложность**: Средняя  
**Импакт**: Средний

## Категория 2: Архитектура и качество кода

### 2.1 Аллокации в игровом цикле — GC-дёрганье

**Описание**: В game.js:201 на каждый кадр создаётся `new THREE.Vector3(behindX, 3.5, behindZ)` для camera.lerp(). Это ~60 аллокаций/сек, которые давят на сборщик мусора и могут вызывать микро-фризы.

**Обоснование**: Это классическая ошибка в Three.js-проектах. V8 GC в Chrome может вызывать frame drops при частых мелких аллокациях в горячем пути.

**Что сделать**:
- Вынести вектор в модульную переменную (`const _tmpVec = new THREE.Vector3()`) и переиспользовать через `.set()`
- Провести аудит всех горячих путей (update, render, updateRemoteMeshes) на предмет аллокаций

**Сложность**: Низкая  
**Импакт**: Средний  
**Приоритет**: 🟢 Желательный

---

### 2.2 Отсутствие клиентских тестов

**Описание**: server/test_server.js содержит 35 интеграционных тестов для серверной части. Для клиентского кода (game.js, car.js, track.js, network.js, ui.js, minimap.js) — ноль тестов.

**Обоснование**: CarPhysics — чистая логика без DOM-зависимостей, идеально тестируемая. Track.project(), Track.wallHit(), lap detection — критическая логика без покрытия. Баг с инвертированными A/D (t_ab19e7ce) мог быть пойман юнит-тестом.

**Что сделать**:
- Юнит-тесты для CarPhysics: ускорение, торможение, поворот, дрифт, столкновение со стеной, завершение круга
- Юнит-тесты для Track: project() возвращает корректный lateral/trackT, wallHit() корректно пушит назад
- Достаточно vitest/jest + jsdom (или headless, т.к. CarPhysics не зависит от DOM)

**Сложность**: Низкая  
**Импакт**: Средний  
**Приоритет**: 🟢 Желательный

---

### 2.3 Монолитный index.html — вся логика вплетения в один файл

**Описание**: client/index.html (~410 строк) содержит: CSS стили, HTML-разметку, inline `<script type="module">` с ~130 строками бизнес-логики подключения, управления комнатами, обработки сетевых событий. Модули (game.js, network.js, ui.js) хорошо разделены, но «клей» между ними живёт в HTML.

**Обоснование**: Текущая архитектура «без build step» — это явный плюс проекта. Но inline-скрипт уже достаточно велик и содержит дублирование (MAP_NAMES в HTML повторяет MAP_INFO в ui.js). При добавлении фич (звук, AI, settings) этот блок вырастет неуправляемо.

**Что сделать**:
- Вынести inline-скрипт в `client/src/main.js` (один import в HTML)
- CSS вынести в `client/style.css`
- Единый MAP_INFO — только в одном месте (ui.js), реэкспортировать в main.js
- Сохранить «zero build step» — importmap + ES modules

**Сложность**: Низкая  
**Импакт**: Средний (maintainability)  
**Приоритет**: 🟢 Желательный

---

### 2.4 Серверная валидация кругов — доверие клиенту

**Описание**: Завершение круга (lap_complete) приходит от клиента, и сервер принимает его безусловно (server.js:430-438). Клиент может отправить 3 lap_complete подряд и мгновенно «выиграть» гонку.

**Обоснование**: Для LAN-игры между друзьями это допустимо, но для любого публичного деплоя — дыра. Результаты записываются в leaderboard без проверки.

**Что сделать**:
- Серверная проверка: минимальный интервал между lap_complete (например, > 5 секунд)
- Rate limit на lap_complete (не чаще 1 раз в N секунд)
- Опционально: сервер отслеживает trackT из state_update и проверяет пересечение start-finish

**Сложность**: Низкая  
**Импакт**: Средний  
**Приоритет**: 🟡 Важный

## Категория 3: Пользовательский опыт (UX)

### 3.1 Мобильные устройства — полностью не поддерживаются

**Описание**: Нет тач-управления. Нет viewport meta-тега (кроме charset). Нет gamepad API. На мобильном устройстве игра рендерится, но управлять невозможно.

**Обоснование**: WebGL и Three.js отлично работают на мобильных браузерах. Тач-управление для гоночной игры — стандарт жанра (виртуальный джойстик или наклон акселерометра). Это огромная аудитория.

**Что сделать**:
- Touch-контроллер: левый полуэкран — руль (tilt/swipe), правый — газ/тормоз (кнопки)
- `<meta name="viewport" content="width=device-width, initial-scale=1">` + адаптивный CSS для UI-скринов
- Gamepad API — navigator.getGamepads() для контроллеров (Xbox/PS)
- Акселерометр как опциональный руль (DeviceOrientationEvent)

**Сложность**: Средняя  
**Импакт**: Высокий  
**Приоритет**: 🟡 Важный

---

### 3.2 Настройки игрока — нет персонализации

**Описание**: Игрок не может выбрать цвет машины (назначается сервером по порядку подключения), не может настроить чувствительность руля, не может отключить CRT-шейдер через меню (только Tab). Нет экрана настроек.

**Обоснование**: Персонализация повышает вовлечённость. Цвет машины — минимальная кастомизация, но значимая для идентификации в мультиплеере.

**Что сделать**:
- Экран настроек в UI: выбор цвета машины, переключатель CRT, громкость (когда появится звук)
- Сохранение в localStorage (имя, хост, цвет, настройки)
- Передача выбранного цвета на сервер при join

**Сложность**: Низкая  
**Импакт**: Средний  
**Приоритет**: 🟢 Желательный

---

### 3.3 Reconnect и устойчивость сети

**Описание**: При разрыве соединения (network.js:27-29) вызывается stopSync() и fire('disconnected'), клиент показывает экран подключения с ошибкой. Автоматического переподключения нет. Если соединение дрогнуло на 1 секунду — гонка потеряна.

**Обоснование**: В LAN-среде разрывы редки, но Wi-Fi — реальность. Reconnect с восстановлением состояния значительно улучшит опыт.

**Что сделать**:
- Auto-reconnect с exponential backoff (3 попытки)
- На сервере: сохранять состояние игрока 30 секунд после disconnect, позволять re-join по playerId
- На клиенте: при reconnect запрашивать текущее состояние гонки и восстанавливать позицию

**Сложность**: Высокая  
**Импакт**: Средний  
**Приоритет**: 🟢 Желательный

---

### 3.4 Нет обратного отсчёта до начала — игрок сразу едет

**Описание**: В одиночном контексте (без мультиплеера) нет стартового обратного отсчёта. Гонка начинается мгновенно. В мультиплеере обратный отсчёт есть (countdown screen), но после «GO!» нет короткой задержки — игроки стартуют, пока анимация ещё играет.

**Обоснование**: Стартовый обратный отсчёт — стандарт жанра. Даёт время оценить трассу и создаёт напряжение.

**Что сделать**:
- При запуске гонки: заморозить ввод на 3-2-1-GO, показывать обратный отсчёт на HUD
- Звуковой сигнал на каждую цифру (при реализации п.1.1)
- «GO!» разблокирует ввод

**Сложность**: Низкая  
**Импакт**: Средний  
**Приоритет**: 🟢 Желательный

## Категория 4: Контент и расширяемость

### 4.1 Неиспользованный потенциал темизации карт

**Описание**: MAPS.md определяет `theme` с полями skyColor, groundColor, ambientColor, fogDensity. В JSON-файлах карт (desert_drift.json, cyber_highway.json) есть theme-данные. Но клиент их полностью игнорирует — sky, grid, background одинаковы на всех картах (хардкод в game.js:createSky, createGrid).

**Обоснование**: Карты визуально неразличимы (кроме формы трассы и пропсов). Desert Drift должен иметь пустынное небо и песчаный грунт, а не тот же фиолетовый синтвейв.

**Что сделать**:
- Читать theme из trackData в initGame()
- createSky(): использовать skyColor для градиента
- createGrid(): использовать groundColor для подложки
- Опционально: fog (scene.fog = new THREE.FogExp2(color, density))

**Сложность**: Низкая  
**Импакт**: Высокий  
**Приоритет**: 🔴 Критический

---

### 4.2 Редактор трасс — нет инструментов создания контента

**Описание**: Карты создаются вручную в JSON (centerline координаты, пропсы). Нет визуального редактора, нет инструмента предпросмотра. SVG-превью генерируются отдельным Python-скриптом (generate_previews.py).

**Обоснование**: Пользовательский контент (UGC) — главный источник реиграбельности для гоночных игр. Текущий формат карт (MAPS.md) хорошо документирован и достаточно прост для визуального редактора.

**Что сделать**:
- Простой встроенный редактор: canvas-based, рисование centerline кликами, drag контрольных точек
- Мгновенный 3D-предпросмотр (инстанцировать Track из нарисованных точек)
- Export/import JSON
- Опционально: шаринг карт через сервер (REST endpoint для upload/download)

**Сложность**: Высокая  
**Импакт**: Высокий  
**Приоритет**: 🟢 Желательный (долгосрочно)

### 4.3 Дополнительные типы пропсов

**Описание**: track.js:_props() обрабатывает 4 типа: tree, building, neon_sign, light_pole. MAPS.md определяет ещё: cactus, rock, ramp, bridge, barrier — все они игнорируются рендерером.

**Обоснование**: Desert Drift должен иметь кактусы, Cyber Highway — мосты и барьеры. Без них карты визуально бедны за пределами трассы.

**Что сделать**:
- Реализовать оставшиеся типы пропсов в track.js:_props() (простая box-геометрия, как для tree/building)
- cactus: зелёный цилиндр/бокс
- rock: серый скруглённый бокс
- barrier: низкий широкий бокс с полосами
- bridge: П-образная конструкция над трассой

**Сложность**: Низкая  
**Импакт**: Средний  
**Приоритет**: 🟡 Важный

9. Одиночный режим с AI (1.4)

**Фаза 4 — Platform features:**
12. Настройки (3.2), reconnect (3.3), тесты (2.2)
